# PingPong

A C client/server network lab implementing TCP and UDP communication, plus a bash script that plots measured throughput against a latency-bandwidth model.

## Overview

The goal of the "PingPong" lab is to build a reliable data network using the C programming language. The network transmits data between devices through a **server** and a **client**, implemented for two transport protocols:

| Protocol | Characteristics |
|----------|-----------------|
| **UDP** (User Datagram Protocol) | No stable or secure connection. Data is sent as independent packets with no delivery guarantee. Its main strength is speed. |
| **TCP** (Transmission Control Protocol) | Reliable: a stream connection is established between sender and receiver before any data is sent, and data is delivered in sequence. |

## Implementation

The project was developed in three steps:

1. **TCP client.** Built on top of the provided code, using system calls that were new to us. The Linux manual pages were the main reference for using them correctly.
2. **UDP client.** The main difficulty was handling the **timeout**, which lets the client retry sending packets that were lost.
3. **Server.** Needed to simulate a client-server connection. Early problems with `accept` being interrupted were caused by a wrong use of `getaddrinfo` (the server's own address must be assigned), which made `bind` fail and, as a consequence, `accept` as well. Fixing the first error resolved the other two.

## Graph generation

A bash script generates a graph of the measured throughput (log scale) against message size, and compares it with a theoretical latency-bandwidth model.

The scripts and executables mentioned in the report are:

- `tcp_ping` and `gc_tcp_ping`: the TCP executables used to collect the data
- `tcp_vers2.bash`: the script that produces the restricted TCP graph (see below)

### Model

Throughput and delay are related to the message size N (in bytes) by:

```
T(N) * D(N) = N
```

Using the median throughput, the delay is computed for the maximum and the minimum message size. Combined with the latency-bandwidth model

```
D(N) = L + N/B
```

this gives a linear system, which is solved for bandwidth (B) and latency (L):

```
B = (Nmax - Nmin) / (D(Nmax) - D(Nmin))
L = (D(Nmin) * Nmax - D(Nmax) * Nmin) / (Nmax - Nmin)
```

The theoretical throughput plotted in the graph is then:

```
f(x) = x / latency + x / bandwidth
```

where `x` is the message size.

Each graph compares three series: **median throughput**, **average throughput** and the **latency-bandwidth model**.

## Results and known issues

- **UDP:** the graph covers messages from 48 to 1024 bytes, because larger datagrams were systematically blocked by the network. The model and the measured curve meet at the start and end points and differ in between, because of both our code and the network.
- **TCP:** with the full range of sizes, the model curve looks like a straight line instead of a logarithmic one. The throughput at 32 bytes is lower than 1, which produces a negative bandwidth, and that is not allowed. The workaround was to **exclude messages smaller than 48 bytes**, which gives a more plausible result (generated by `tcp_vers2.bash`). Why this happens with both `tcp_ping` and `gc_tcp_ping` is still unclear.
- **Test environment:** experiments were run against `seti.dibris.unige.it` instead of `localhost`. On localhost the bandwidth can reach huge values and the latency is always close to 0, which makes the results unreliable. Even so, the UDP results are not entirely reliable.
